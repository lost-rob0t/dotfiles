* Important invariants
The repository editing rules require Qtile sync/reload behavior to:
- use the shared =git-sync= implementation;
- avoid blocking Qtile's event loop while Git runs;
- reload only after a successful sync;
- send desktop notifications for start, success, and failure.

OpenRouter telemetry is rate-oriented rather than balance-oriented. The bar reports prompt and completion tokens from the trailing 60-second window as tokens per minute, polls the analytics helper every five seconds, and graphs five minutes of sampled rates. The balance and 30-day counters are deliberately omitted. The graph suppresses constant series and adaptively scales moving series so a much larger prompt stream does not visually erase completion traffic.

The dynamic =Super+Ctrl+Shift+R= binding belongs to the OpenRouter telemetry helper.  Keep its documentation and generated implementation synchronized with =qtile-openrouter.org=.

The audio bar widget replaces the stock =Volume= widget because =amixer set Master= cannot address PipeWire outputs.  =qtile_audio.py= talks to =pactl= and always targets =@DEFAULT_SINK@=: left click opens a =Popup= dropdown of every sink and selecting one runs =pactl set-default-sink= plus a pinned preference under =$XDG_STATE_HOME/nsa-qtile/=, scroll changes volume, middle click toggles mute.  All =pactl= calls run in the poll thread or an executor (the cached sink list feeds the dropdown), so the Qtile event loop never blocks.  Tests: =tests/test_qtile_audio.py= covers parsers, click-path structure, and Org/generated parity.

* Topics
Groups are mapped to named topics.  The declarative registry =DEFAULT_TOPICS=
lives in [[file:../../.config/qtile/qtile-ai.org][qtile-ai.org]]; each topic generates one prefixed group =t:<name>= after
the static ="1".."0"= workspaces, so the pool scales without keybinding or
bar collisions.  The initial pool: =zara=, =dotfiles=, =prolog-rlm=,
=symbolic-memory=, =quasar=, =tek9=, =zara-plugins=, =starintel=, plus the
generic =comms=, =media=, =web=, =scratch=.

- =all_group_names()= is the single helper every =group_names= consumer uses
  for the extended set (bar =OwnedGroupBox= filter, auto layouts, telemetry
  =session_start=).  Static workspaces, =workflows.json= screen mapping, and
  the generated =Mod+1..0= bindings are unchanged; topic groups have no
  digit bindings.
- =OwnedGroupBox= only renders groups with live windows, so empty topics do
  not clutter the bar.
- Topic groups are exempt from Auto routing: windows placed in a topic stay.
- Keybindings: =Mod+g g= jump (Emacs picker), =Mod+g n=/=Mod+g p= next/prev
  topic, =Mod+g t= toggle the Emacs topics dashboard, =Mod+Shift+g= move the
  focused window to a topic.
- Runtime management is exposed on the IPC root for the Emacs UI and shell:
  =qtile cmd-obj -o cmd -f create_topic|remove_topic|focus_topic|send_to_topic -a <name>=.

The topics dashboard and picker are provided by
[[file:../../lisp/qtile/qtile-topics.el][lisp/qtile/qtile-topics.el]] on top of the shared popup lifecycle (see
[[file:../qtile-emacs-ui.org][Qtile and Emacs dropdown UI]]).

* Streamer mode
Streamer mode is a session-only privacy gate for the recorded center screen.
It is OFF on every Qtile start and a config reload resets it.  While armed,
only allow-listed windows may occupy the group shown on the =center= role's
screen (resolved via =screen_roles()=); anything else landing there is moved
to the =hold= group on another screen — never killed.  Enabling sweeps
existing violations off center.  The allow-list classifier and
=STREAM_ALLOWLIST= constant live in [[file:../../.config/qtile/qtile-ai-windows.org][qtile-ai-windows.org]].

| Window | Allowed while streaming |
|--------+-------------------------|
| Nyxt browser (=Nyxt= / =nyxt= class) | yes |
| Stream Emacs (frames named/classed =StreamEmacs=) | yes |
| OpenCode (=terminator= titled =OpenCode=) | yes |
| Brave, KeePassXC, Discord, generic terminals, everything else | no |

- Bar: a = STREAM = toggle button sits next to =AUTO= (same callback style;
  the armed state paints the accent color for an unambiguous center
  indicator).
- Keys: =Mod+s= toggles; =Mod+Shift+s= toggles plus starts
  =screen-capture record-screen= and stops it on disable (only recordings
  the streamer started; the X11 recorder captures the monitor under the
  pointer, so keep the pointer on center when arming).  Both recording
  calls spawn without blocking the event loop.
- =Mod+u= launches the chrooted Doom stream Emacs:
  =.config/qtile/scripts/stream-emacs= runs Emacs inside bubblewrap with
  only =~/Documents/Projects= and =~/starintel= bound read-write, a tmpfs
  =HOME=, read-only Doom config/core with writable state overlays, and the
  X11/Wayland sockets shared.  Its server name is =stream= and frames are
  named =StreamEmacs= (=scripts/stream-emacs-init.el=), which is what the
  allow-list matches.

* Desktop workflows
The Emacs-backed workflow picker reads the tangled =workflows.json=.  The
lifecycle extension in =qtile_workflows.py= keeps screen placement delegated to
the existing =qtile_control.py= layer while allowing a workflow to request
client cleanup, an explicit Auto-mode state, persistent per-group layout
overrides, and non-blocking application launches.

The =starintel= workflow is a clean-room desktop rebuild.  Selecting it closes
all managed client windows, forces Auto mode on, places groups 1/2/3 on the
left/center/right screens, keeps group 3 in =max= while the workflow is active,
and launches:
- Brave on group 1 at =https://git.starintel.actor=;
- a new Emacs client frame on group 2 visiting =~/starintel=;
- one Terminator on group 3 titled =OpenCode=, running =opencode= from
  =~/starintel=.

The OpenCode title is intentional: Auto routing recognizes OpenCode terminal
windows as AI windows, so the normal routing policy remains authoritative after
the workflow has bootstrapped the desktop.  Selecting another workflow clears
the Star Intel group-layout override and restores the normal adaptive layout
policy.

* OpenCode web workspace
The desktop Home Manager profile enables a persistent =opencode-web= systemd
user service through Home Manager's native =programs.opencode.web= support.  It
is pinned to =127.0.0.1:4096=, so the API and browser UI are reachable only from
the local machine by default.  No server password is required for this
loopback-only deployment; authentication must be added before changing the
listener to a LAN-facing address.

Home Manager also installs an =OpenCode Web= desktop entry.  It runs
=opencode-web-open=, which opens =http://127.0.0.1:4096= in the configured
browser.  The =opencode-attach= command connects a TUI to that persistent
backend so the browser and terminal share the same server-side session state.

Useful checks after switching the profile:

#+begin_src shell
  systemctl --user status opencode-web.service
  curl -I http://127.0.0.1:4096/
  opencode-attach
#+end_src

* Auto workspace routing
The Qtile Auto mode button routes newly managed windows while it is enabled;
it does not poll or repeatedly reorganize existing windows.  AI-related
windows go to workspace 3, Discord goes to workspace 9, games go to workspace
4, and video players or video-site tabs go to workspace 6.  This includes
ChatGPT Desktop, AI tabs in Brave, T3 Code, Emacs LLM/OpenRouter/MCP buffers,
OpenCode or Claude Code terminal windows, Steam/PrismLauncher/Minecraft/War
Thunder, and YouTube/Twitch tabs.
The matcher is maintained in [[file:../../.config/qtile/qtile-ai-windows.org][qtile-ai-windows.org]] and tangles to [[file:../../.config/qtile/qtile_ai_windows.py][qtile_ai_windows.py]]; it was seeded from the local ActivityWatch window bucket.
Ordinary Brave pages and terminal windows are not routed by title alone.  The
focused newly routed window follows its destination group so it does not
appear to disappear from the current screen.

The Bash =opencode= command runs the executable directly in the current
terminal; =oc= is a short alias for it.  Use =opencode-attach= when the TUI
should join the persistent web backend.  Qtile's =Super+T= binding launches a
separate Terminator window.

* Desktop integration map
Qtile-related files live under [[file:../../.config/qtile/][.config/qtile/]].  Besides the generated main config, that tree contains widgets, helper scripts, icons, autostart integration, and support code.

Related desktop configuration is spread through =.config/= and Home Manager modules.  Before moving a file into Home Manager, check whether it is currently Stow-managed.  Avoid creating two deployment owners for the same path.

* Edit and test cycle
1. Edit the relevant Qtile Org source.
2. Tangle it.
3. Confirm only the expected generated Python/JSON files changed.
4. Compile the generated Python.
5. Run the Qtile workflow regression/parity tests when workflow behavior changed.
6. Exercise the affected keybinding/widget/hook in a running Qtile session.

#+begin_src shell
  cd ~/.dotfiles
  python -m py_compile .config/qtile/config.py
  python -m py_compile .config/qtile/qtile_openrouter.py
  python -m py_compile .config/qtile/qtile_workflows.py
  python -m py_compile .config/qtile/qtile_ai_windows.py
  python -m unittest discover -s .config/qtile/tests -p 'test_qtile_workflow*.py' -v
#+end_src

For a sync/reload change, test both successful and failed Git sync paths so notification and reload behavior do not quietly rot.
