#+title: Distro release engineering — the dotfiles as a meta-distro

The dotfiles repository is declared a *meta-distro*: it versions itself,
tracks feature/bug requirements, and releases only through an enforced
gate.  Humans file issues stupid-easy; agents do the work; a council of
agents attacks the code and votes; Prolog has the final say.

Canonical parts:

- =issues.org= — intake + tracking ledger (human-facing)
- =scripts/distro= — the CLI (literate source =scripts/distro.org=)
- =distro/config.pl= — release policy the human owns (quorum, attack steps)
- =distro/engine/= — the Prolog engine (loader, model, gates, version, report)
- =distro/VERSION=, =distro/CHANGELOG.org=, =distro/archive/= — release state
- =.opencode/skills/distro-work=, =.opencode/skills/distro-council= — agent protocols
- =tests/distro-test.sh= — end-to-end suite (also an attack-suite step)
- =.doom.d/autoload/distro.org= — Emacs/gptel frontend (→ =distro.el=)

* Pipeline

#+begin_src text
human one-liner ──▶ issues.org (* Inbox)
                        │  distro triage (assigns ISSUE-nnnn, milestone)
                        ▼
                 issues.org (* Tracked)
                        │  distro sync (compiles Org → facts)
                        ▼
            distro/state/facts.pl + journal.pl   (epoch-stamped)
                        │
                        ▼
            distro/engine (SWI-Prolog) ── release gates
                        │
        agents: claim → implement → verify evidence → done
        council: attack suite + votes (epoch-bound)
                        ▼
            release_ready(M) = yes
                        │  distro release --yes
                        ▼
        VERSION = M, entries archived to distro/archive/,
        old requirements stop being tracked, changelog written
#+end_src

* Why Prolog, and how agents use it

The engine is a plain SWI-Prolog program.  Any agent — any harness — gets
two entrances:

1. *CLI* (works everywhere): =distro status=, =distro next=, =distro
   release= ...  The script only obeys the engine; it has no authority of
   its own.
2. *Live Prolog session* (preferred for reasoning): load the engine and
   query predicates directly — structured answers, not scraped text:

   #+begin_src prolog
   ?- [distro/engine/engine].
   ?- distro_root(R).
   ?- release_blocker('0.2.0', B).   % one answer per blocking reason
   ?- release_ready(M), next_issue(ID).
   ?- reload_distro_state.           % after any state change
   #+end_src

   This was verified through OpenCode's =prolog= MCP: =create_session=
   with the engine path, then =run_goal= over =distro_root/1=,
   =release_target/1=, =release_blocker/2=, =next_issue/1=.  This is the
   prolog-RLM pattern applied for real: gates as facts an agent can prove
   over, with =trace_goal/2= available to explain *why* a gate blocks.

* The epoch invariant

=epoch = sha256(issues.org)[0:16]=, regenerated by =distro sync=.  Votes,
evidence and attack results all record the epoch they observed.  Change
=issues.org= and every observation made against the old state silently
stops counting.  Consequences:

- Council votes are for an exact tracked state, not a milestone in
  general.
- "Done" evidence must postdate the last ledger change affecting the
  issue's milestone... in practice: re-verify after edits; the gate
  refuses stale facts and =distro status= names them.

* Council policy

- =council_quorum(2)= — distinct councilors must approve (config.pl).
- Last vote per councilor wins; any standing reject blocks.
- The attack suite (=attack_step/1= facts) must be green at the current
  epoch.  Councilors attack the *code* before PRs: read diffs, grill
  invariants, run the suite, report defects on the issue, reject when
  broken.
- Agents never weaken =config.pl= to pass a gate; that file is the human's.

* Release mechanics

=distro release --yes= requires =release_ready/1=.  Then it: bumps
=distro/VERSION= to the milestone, moves the milestone's tracked entries
to =distro/archive/v<M>.org= (old requirements stop being tracked — never
hand-deleted), writes =distro/CHANGELOG.org=, appends a =release/3= fact
to =distro/archive/releases.pl=, resets the journal, and optionally tags
=distro-v<M>= with =--tag=.  A pure-bug milestone still lands on its
milestone number; default milestones are next-minor so distro versions
move one minor per default cycle.

* Human workflows (stupid-easy)

- Shell: =distro feat "..."= / =distro bug "..."=
- Emacs: =M-x distro-feat=, =M-x distro-bug=, =M-x distro-status=, org
  capture templates =df=/=db=, =M-x distro-gptel-draft= (gptel expands a
  one-liner into a well-formed issue)
- Plain org: write =** BUG: something broke= under =* Inbox=, done.

* Agent workflows

- Implementation: follow =.opencode/skills/distro-work=
  (claim → literate implement → =distro verify= evidence → =distro done=).
- Review/release: follow =.opencode/skills/distro-council=.

* Deliberate non-goals / related files

- =tasks.org= is the human's personal Emacs command file (babel blocks,
  gptel helpers) — it is NOT the intake and never a work queue.  The
  cross-repo contract for it lives in the global agent policy
  (=nix/home-manager/files/global-agents.md=).
- Issue bodies and statuses live in =issues.org=; the state under
  =distro/state/= is generated and untracked; do not hand-edit it.
