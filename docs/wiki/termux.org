* Purpose

This page is the operational map for the custom Termux family shipped from this
dotfiles repository.  The executable source of truth remains
[[file:../../android/build.org][android/build.org]] and the paired GitHub workflow.  This page documents how the
pieces fit together, what each companion app is for, and the install/upgrade
invariants that are easy to forget on Android.

The family is source-built and re-signed together.  Do not mix an APK from this
bundle with F-Droid, Google Play, or upstream GitHub APKs from another signing
identity.

* Family architecture

The release family contains native GNU Emacs plus Termux and six Termux
companions.  Every APK is verified before publication for:

- the expected Android package identity;
- =android:sharedUserId=com.termux=;
- ZIP alignment;
- exactly one signing certificate shared across the whole family;
- a SHA-256 artifact digest recorded in =PAIRING.json=.

The build resolves the latest stable upstream release tag for each Termux
repository at workflow runtime and writes the exact tag and commit SHA to
=SOURCE-LOCK.txt=.  That keeps the build current without making this wiki a
second version database.

| App | Android package | Role in this setup |
|-----+-----------------+--------------------|
| GNU Emacs | =org.gnu.emacs= | Native Doom-free Org/Vim reader with access to the paired Termux toolchain. |
| Termux | =com.termux= | Native shell, language toolchains, SSH, tmux, Git, Prolog, Lisp, Nim, Python, and bootstrap runtime. |
| Termux:API | =com.termux.api= | Android device/API bridge for Termux commands after the user grants Android permissions. |
| Termux:Widget | =com.termux.widget= | Home-screen foreground shortcuts and background tasks from =~/.shortcuts/=. |
| Termux:Boot | =com.termux.boot= | Runs explicitly configured scripts from =~/.termux/boot/= after Android boot. |
| Termux:Float | =com.termux.window= | Floating terminal window for quick shell/admin work over other apps. |
| Termux:Styling | =com.termux.styling= | Termux font and color selection.  It complements, rather than replaces, dotfiles-owned shell/editor themes. |
| Termux:Tasker | =com.termux.tasker= | Bridge that lets Tasker/Locale-style automation invoke allowed Termux commands.  Tasker itself is not bundled. |

* Canonical implementation

- [[file:../../android/build.org][android/build.org]] owns =android/build.py= and the package/signing verification gate.
- [[file:../../.github/workflows/android-emacs-release.yml][android-emacs-release.yml]] resolves upstream release refs, clones sources, builds every APK, signs the family, verifies it, and publishes bundles.
- [[file:../../android/tests/test_termux_build.py][android/tests/test_termux_build.py]] checks the package family, manifest parser, signing behavior, and literate/generated parity.
- [[file:../../bootstrap-termux.org][bootstrap-termux.org]] owns the Termux userspace/bootstrap after the APK family is installed.
- [[file:../../scripts/termux-remote.org][scripts/termux-remote.org]] owns the remote GUI, Agent Zero tunnel, and extra Termux:Widget shortcuts.
- [[file:../../android/README.org][android/README.org]] owns the broader native-Emacs/Termux install and profile workflow.

* Build and release flow

The workflow performs these steps as one release unit:

1. resolve stable source tags for Termux, API, Widget, Boot, Float, Styling, and Tasker;
2. source-build GNU Emacs and every Termux application;
3. record source refs and commit SHAs in =SOURCE-LOCK.txt=;
4. align and sign every APK with the repository's configured persistent Android key;
5. inspect every manifest and certificate with Android SDK tools;
6. write =PAIRING.json= and =SHA256SUMS=;
7. publish only after the complete family passes verification.

A tagged =android-emacs-v*= release refuses the public TEST-ONLY compatibility
key.  The public key path exists only for explicit manual CI smoke builds.

* Install and upgrade invariant

Android signing identity and shared-user membership are installation-time
contracts.  Back up Termux home and important Android app data before switching
families.

Install APKs from one generated bundle together.  Android will reject an upgrade
signed with a different key, and uninstalling Termux can delete app data.  The
build workflow therefore never installs or uninstalls apps automatically.

A practical install order is:

1. Termux;
2. API, Widget, Boot, Float, Styling, and Tasker;
3. native GNU Emacs;
4. launch Termux and Emacs once;
5. run [[file:../../bootstrap-termux.org][the Termux bootstrap]];
6. run =android-emacs-stow=;
7. smoke-test =git --version= in Termux and =M-! git --version= in native Emacs.

The certificate/shared-UID gate is more important than the order: every installed
member must come from the same bundle.

* Companion workflows

** Termux:Widget

The bootstrap creates the core shortcuts, while
[[file:../../scripts/termux-remote.org][scripts/termux-remote.org]] adds the remote-workflow layer.  Foreground shortcuts
live in =~/.shortcuts/= and background tasks in =~/.shortcuts/tasks/= with mode
=0700=.

Current workflows include Org capture, SSH to =flake=, remote ChatGPT launch,
Agent Zero tunneling, dotfiles refresh, StarIntel admin, agenda/TODO access, and
AI entry points.

** Termux:Boot

Boot is intentionally opt-in.  Put only small, idempotent launchers in
=~/.termux/boot/=.  Long-lived work should immediately hand off to tmux or a
service supervisor so Android boot does not become a giant shell script.

Good candidates are restoring a local tmux control session, starting =sshd= when
you explicitly want it, or scheduling local sync/service startup.  Do not put
secrets in boot scripts and do not start remote tunnels merely because the phone
rebooted unless that behavior is intentional.

** Termux:Float

Float is the fast shell surface: use it for a short admin command, attaching to
an existing tmux session, or checking a remote job without switching fully into
Termux.  Android's overlay permission must be granted by the user.

** Termux:Styling

Styling owns Termux's Android-terminal presentation.  The shell, Doom, Qtile,
and Zara themes remain dotfiles-owned configuration.  This separation prevents a
phone font/color picker from becoming another source of truth for editor or
desktop theme behavior.

** Termux:Tasker

Tasker integration is an external automation bridge, not a replacement for the
Prolog/Zara automation model.  Keep callable scripts small and explicit, and
route durable behavior through the same dotfiles commands used interactively.
That makes a Tasker action a thin trigger instead of a hidden second
implementation.

** Termux:API

API commands cross from the Termux shell into Android facilities such as
notifications, intents, sensors, clipboard, and media.  Android permission
prompts remain user-controlled.  Scripts should fail clearly when a permission
or API package is unavailable instead of silently degrading.

* Troubleshooting

** Plugin says Termux is incompatible

Check that the plugin APK and Termux APK came from the same generated release.
The most common cause is mixing signing families.

** Native Emacs cannot execute Termux Git

Verify that the paired family is installed, then follow
[[file:../../android/README.org][android/README.org]] for the shared-UID bridge and run =android-emacs-stow= again.

** Widget entries are stale

#+begin_src sh
git -C ~/.dotfiles pull --ff-only
bash ~/.dotfiles/scripts/install-termux-widgets
#+end_src

** Build artifact identity

Inspect =PAIRING.json= first.  It is the machine-readable statement of the APK
set, expected package identities, hashes, shared user, and signing certificate.
=SOURCE-LOCK.txt= answers the separate provenance question: exactly which
upstream sources were built.

* Archive collection at boot

[[file:../../scripts/termux-starintel.org][scripts/termux-starintel.org]] owns the cron/runit integration and its generated
=termux-starintel= command. The bootstrap installs =cronie=, =termux-services=,
=coreutils= and =util-linux=, then invokes that helper. Existing setups can run
=bash ~/.dotfiles/scripts/termux-starintel install= directly after installing the
service dependencies. Fresh installs clone the pinned public
[[https://github.com/lost-rob0t/election26/blob/5d8d9659acea6349adc6f264b35964ef7309f004/scripts/install-termux.sh][election26 Termux installer]] and invoke =--install --if-needed=. The upstream
installer owns the managed venv/launcher, official package checks, and create-once
private defaults. Dotfiles does not embed or fork its implementation.

Fresh installs use =~/.config/election26/config.json= and
=~/.local/share/election26/archive/=. The initial host allowlist and feed list
are empty; configure selected sources before expecting stored objects. No paid
API, Discord, media download or remote access is enabled. The existing phone's
=~/starintel/ops/archive-config.json= and =~/starintel/ops/archive/= select the
legacy profile. That pair and any existing collector executable are preserved;
an incomplete legacy pair fails instead of creating an alternative archive.
The selected profile is saved in =~/.local/state/termux-starintel/profile=.
Upstream's standard Android HOME/PREFIX guard remains unchanged; relocated or
nonstandard Termux installs are not supported by that installer.

Installation backs up the crontab to =~/.local/state/termux-starintel/crontab.*=,
wraps one recognized collector command without changing its schedule or
arguments, and preserves unrelated lines. An absent collector entry receives
one every-five-minute RSS entry. Ambiguous entries and an in-flight legacy
collector abort with a diagnostic; allow that run to finish and retry. No archive
migration, copy or cleanup of an existing archive is performed. =~/2026/= and
the existing archive remain in place. Fresh setup creates only the upstream
standard empty archive and default config. The reported 246 stored objects / 247
observations / zero errors are prior phone evidence, not results of this patch.

During handoff the installer also holds the wrapper lock and an existing
canonical archive =.writer.lock= read-only. It checks same-UID bare/absolute
collector processes before and after changing cron. A migration marker keeps
new wrappers blocked if handoff is interrupted; retry once the legacy run has
finished. Process matching is observational, not a perfect lock for arbitrary
old/manual invocations. The maintained collector has its own archive writer
lock. Quiesce independent/manual launchers before migration; no old process is
killed.

The wrapper serializes runs with =flock= and applies a 240-second timeout with
a ten-second kill grace. Failures retry on the next scheduled tick. Collector
output goes to =$PREFIX/var/log/sv/election26/= through =svlogd=; collector and
crond logs each retain a 1 MB current file and three rotated files. An already
running supervised cron logger receives a targeted HUP to apply its new config.
Existing shell redirections are preserved; historical output files are not deleted.
Network availability is exercised by the collector's own request handling;
there is no unrelated public-host ping or new collection source.

| Command | Effect |
|---------+--------|
| =termux-starintel status= | Check config, supervisor and crond process; show pause state and log location. |
| =termux-starintel logs= | Show the last 80 collector log lines. |
| =termux-starintel stop= | Pause future wrapped collections; other cron entries continue, an in-flight run finishes. |
| =termux-starintel start= | Resume collections and ensure cron startup. |
| =sv status crond= | Inspect the packaged daemon service. |
| =sv-disable crond= | Stop supervised cron until this bootstrap starts/enables it again; affects all its jobs. |

If crond was started manually, installation retains it and does not launch a
second daemon. The supervisor PID must also match the intended executable,
UID and service directory; a reused PID is not trusted. Installer lock file
descriptors are closed before daemon startup. The next boot starts the packaged
runit service. A legacy
external crond remains operator-owned; =sv-disable= cannot stop that process.
The managed =~/.termux/boot/20-starintel-services= hook preserves a collector
pause and starts only the service supervisor and cron. Rerunning install also
preserves a pause. Existing boot hooks remain untouched; review any independently
configured legacy cron launch hook to avoid competing startup owners.

Install Termux:Boot from the same signed APK family as Termux, then tap its
launcher icon once. Review Android battery optimization and vendor background
startup settings manually for Termux and Termux:Boot. These app/permission steps
cannot be performed by this shell bootstrap. Android may still suspend/kill
background processes. =termux-wake-lock= is an optional manual power tradeoff;
this hook does not acquire one automatically. See the official
[[https://github.com/termux/termux-boot#how-to-use][Termux:Boot instructions]], [[https://github.com/termux/termux-services][termux-services commands]], and
[[https://github.com/termux/termux-packages/blob/master/packages/cronie/build.sh][packaged crond service definition]]. No remote access service is enabled.

** StarIntel runtime boundary

The supported local workload here is the RSS archive collector, freshly installed
from its pinned upstream installer or reused with its existing private config. It is an archive host, not a complete local
Star Server deployment. Optional remote destinations remain in user-owned
configuration; no endpoint, credential, SSH access or tunnel is enabled by this
patch. Keep credentials out of Git and restrict private config files to their
owner. The collector's archive format is not asserted to be a live server DB.

Source audit (2026-10-17):

- [[https://github.com/lost-rob0t/starintel-edge/blob/0a75eb292b302368a6308b6f53fe2a0fdab34ee0/docs/DISTRIBUTION.md][Edge distribution]] describes Termux as an installer-plan target with service adapters
  incomplete. =starintel-install plan --platform termux= renders a plan; it is
  not a runnable Termux service entry point.
- [[https://github.com/lost-rob0t/starintel-edge/blob/0a75eb292b302368a6308b6f53fe2a0fdab34ee0/docs/ANDROID-SERVICE-EVIDENCE.md][Edge Android evidence]] concerns a separate ECL/JNI Android host. Its local actor
  core does not establish full Star Server or Android mesh availability.
- [[https://github.com/lost-rob0t/starintel-server/blob/54a5f65f0fb3ecc286da6fe426213f015a255562/cli/star-cli.asd][Maintained star-cli]] is a Common Lisp ASDF program with entry point
  =star-cli::main=, not a Python package or shell script. Its remote client
  accepts a base URL and runtime =STAR_SERVER_TOKEN=/=STAR_SERVER_API_KEY=.
  A separately built compatible client can use a remote server; this bootstrap
  does not claim that Linux binary runs under Android or install it untested.
- Full Star Server requires its maintained Lisp runtime and CouchDB/RabbitMQ
  infrastructure. Native Termux SBCL and a full CouchDB/RabbitMQ stack are not
  installed or claimed supported. The existing PRoot/Nix development guest is
  also not evidence of a boot-ready server deployment.

Host validation: =python3 tests/termux-services.py= checks temporary-HOME
installation/reruns, literal source parity, preservation, duplicate prevention,
logging, timeout, stale PID and failure behavior with mocked Termux commands.
=python3 tests/termux-upstream.py /path/to/pinned-election26= additionally executes
the real upstream installer body, setup, receipt, config, launcher and status
through controlled package/Git/venv/pip stubs. Only that test harness substitutes
the hardcoded Android environment gate for a temporary HOME; production does
not bypass it. Both fresh install and verified rerun are checked. These tests
do not establish Android boot, battery survival, actual crond/runit startup,
network collection, collector ABI compatibility or a new object count. On a
test phone/emulator, verify those manually after install, pause/resume, and a
reboot; compare archive/config and =~/2026/= checksums before/after the install
while collection is paused. Do not use a production device as an automatic test
target.

* StarIntel remote operator client

[[file:../../scripts/termux-starintel-client.org][termux-starintel-client.org]] owns the two Termux launchers. The bootstrap installs
=openssl-tool= and exposes the existing tracked
[[file:../../nix/packages/starintel-admin/bin/starintel-admin][starintel-admin CLI]] through Termux Bash. It does not copy or port the CLI.
Installation configures no endpoint, credentials, background process or access
settings and makes no request. An existing unrelated executable is refused;
reruns preserve endpoint/credential environment and user-owned config files.
Existing installations can run =bash ~/.dotfiles/scripts/termux-starintel-client install=
after installing its dependencies: Bash, coreutils, curl, jq, openssl-tool and
Python. No Nix or Lisp runtime is needed for this client.

Configure an endpoint only when wanted. The endpoint must be an explicit HTTPS
base URL without embedded credentials, query, fragment or curl glob syntax.
IPv6 literal authorities such as =https://[::1]:8443= remain valid. For example:

#+begin_src sh
export STARINTEL_ADMIN_URL='https://your-starintel-server.example'
# Set this to an existing owner-private external credential file; do not put a token here.
export STARINTEL_ADMIN_TOKEN_FILE="$HOME/.config/private/starintel-token"
starintel-admin-doctor
# Explicit opt-in request; requires permission to list credential metadata:
starintel-admin-doctor --connect
#+end_src

=STAR_SERVER_URL= is also supported. Credentials can instead come from the existing
=STARINTEL_ADMIN_TOKEN=, =STAR_SERVER_TOKEN= or =STAR_SERVER_API_KEY= environment
variables. Provision them separately through the existing secret-management
workflow. This integration never creates, copies or writes credential values.
An explicit token file must be regular, owned by this UID, inaccessible to group
and others, and outside the checkout and Nix store. The launcher requires an
explicit credential source instead of scanning unrelated infrastructure files.
No shell config or generated launcher stores an endpoint or token. Online CLI
invocations isolate temporary curl credentials in a private directory removed on
exit, including failure. Both online launcher calls and connection diagnostics
force a private curl adapter. It sets =--disable= first so default =~/.curlrc=
files are not read, sets =--globoff= to prevent multi-host URL expansion, allows
only HTTPS, and rejects redirects with a zero redirect budget. Existing curl
configuration is preserved but its trace/output/extra-URL/redirect directives
cannot alter these requests or bypass diagnostic output bounds. An inherited
=STARINTEL_ADMIN_CURL= override is not used on this Termux surface. These curl
semantics follow the [[https://curl.se/docs/manpage.html][official curl manual]].

| Command | Effect |
|---------+--------|
| =starintel-admin --help= / =--version= | Local CLI information; no endpoint or credential needed. |
| =starintel-admin-doctor= | Check dependencies and optional endpoint syntax; make no request. |
| =starintel-admin-doctor --connect= | Invoke the CLI's read-only =key list= API; print success/failure without response bodies. |
| =starintel-admin …= | Run the tracked operator command against the explicit endpoint; normal upstream authorization and command semantics apply. |

The connection diagnostic has a 20-second deadline plus two-second kill grace
and a 1 MiB response cap. Its private temporary directory, including the unchanged
CLI's temporary mode-0600 curl credential config, is removed afterward, including
failure. It changes no users, keys, policies, collection sources or cron jobs.
The full CLI still exposes mutating commands when explicitly invoked; installing
it does not grant server-side authority. See [[file:starintel-admin.org][the existing operator CLI guide]].
The existing =01-StarIntel-Admin= widget continues to open the Org workspace; it
is not redirected to a network request.

This is a remote client. Local Star Server, Edge/Sento, CouchDB, RabbitMQ and
native Lisp runtime installation remain separate work. Existing election26
sources/config/data are untouched; fresh collector defaults remain empty until
sources are selected explicitly.

* Local Server and CouchDB acceptance

Issue [[https://github.com/lost-rob0t/dotfiles/issues/332][#332]] tracks the local Server slice. The chosen deployment candidate is
same-architecture glibc userspace under unprivileged PRoot, with foreground
processes supervised from Termux. It uses the real upstream CouchDB distribution;
it does not substitute a JSON store or a remote Server client. No local Server
service is enabled by the bootstrap yet.

The canonical [[file:../../scripts/termux-couchdb-proof.org][CouchDB acceptance source]] generates
=scripts/termux-couchdb-proof=. This experimental command only checks CouchDB.
Install =proot-distro= 5.9.0 and =proot= in an isolated test environment. On Termux,
=python= and =proot= are available through =pkg=; obtain the exact proot-distro
version in a dedicated Python venv if the packaged version differs. Initial image
installation requires network access and several hundred MB beyond the private
probe data. Do not install over an existing guest. For x86_64:

#+begin_src sh
proot-distro install --name starintel-couchdb-proof --architecture x86_64 docker.io/library/couchdb@sha256:6785bd4bec3d406fbba8d60f8ec258e6ddec38bf0fbfd700916790b697f9ab8e
python3 scripts/termux-couchdb-proof --guest starintel-couchdb-proof \
  --manifest "$PREFIX/var/lib/proot-distro/containers/starintel-couchdb-proof/manifest.json" \
  --state "$HOME/.local/state/starintel-couchdb-proof"
#+end_src

Linux proot-distro stores the manifest under
=${XDG_DATA_HOME:-$HOME/.local/share}/proot-distro/containers/NAME/manifest.json=.
An OCI archive exported with =docker image save= can replace the image argument
for offline installation; retain its manifest/config digest. The installed guest
and cache must already be present for offline reruns. The probe verifies the
installed guest's recorded config digest, not a cryptographic attestation of a
rootfs modified after extraction. Treat guest files as trusted executable code.

The aarch64 candidate uses =--architecture aarch64= and manifest
=sha256:5a1991c184104a164e1df74139989f0bd7c8cac320ac79de3e15cb3c194d3eb4=.
Its config digest is pinned in the source, but it has not been executed here.
No QEMU/cross-architecture runtime support is claimed. Other architectures fail
closed. Both pins are upstream CouchDB 3.5.2 with embedded Erlang OTP 26.

The command starts a dedicated loopback EPMD and CouchDB, waits up to 90 seconds
for readiness, creates one fixture if absent, sends SIGTERM, restarts against the
same private data directory, verifies readback, and stops its own process groups.
SIGINT/SIGTERM also trigger cleanup. A separate live guardian pins each owned
session/group ID even after PRoot exits. A closed pipe gate prevents guest launch
until the guardian handshake, PID registration, and logger setup commit. INT/TERM
are deferred across spawn/registration; constructor failures and interrupted
handshakes reap the still child-free guardian and close startup descriptors. Cleanup sends TERM, allows 15 seconds
for graceful shutdown, then kills the guardian and any remaining group members.
If the guardian is unexpectedly lost, cleanup fails closed instead of signaling
a possibly reused group. Remaining listeners also fail acceptance. The supported
commands run in the foreground; detached processes that create new sessions are
not covered by group supervision. Status is the foreground JSON result/exit status; logs are =couch.log=
and =epmd.log= in the state directory. Re-execute the command to start another
acceptance run. It does not create a detached service or PID-file control API.

Ports 45984 (HTTP), 45969 (EPMD), and 45910 (Erlang distribution) must be free.
All listeners bind to 127.0.0.1; PRoot shares the host network. This does not isolate
other applications running under the same Android UID. A generated private admin
password stays in a mode-0600 state file and HTTP memory; the CouchDB ini contains
only its PBKDF2 verifier. The Erlang cookie is mode 0400. Neither is placed in
source, command arguments, or logs. Managed outputs, rotated log targets and the
lock must be private, regular, singly linked files owned by the current UID.
Symlink/hardlink/nonregular targets fail before writing; descriptor checks and
no-follow opens also protect the actual log/lock file. Logger failures fail
acceptance rather than silently dropping evidence. State must be new or owned by this probe;
existing state and fixture bytes are preserved on rerun.

Each component log rotates at 1 MiB with two backups. The short acceptance run
checks a 128 MiB state budget and 128 MiB free-space reserve at startup/readiness;
these checks are not a hard aggregate filesystem quota. Erlang schedulers are
limited to two. No compaction, backup, production capacity, battery survival, or
Android background-lifecycle guarantees have been established. A production
service needs storage policy, broker readiness and an Android lifecycle test.

** Recorded evidence and blockers (2026-10-17)

- Actual unprivileged Linux x86_64 PRoot, proot-distro 5.9.0, PRoot 5.1.0:
  CouchDB 3.5.2 ready; fixture write; SIGTERM; restart; durable readback passed.
  The checked-in command was run twice against the same state. This is Linux
  execution evidence, not Android execution evidence.
- =python3 tests/termux-couchdb.py= checks exact literate parity, create-once
  state/data preservation, private credentials and digest rejection. These are
  contract tests, not substitutes for runtime evidence.
- Server baseline =54a5f65f0fb3ecc286da6fe426213f015a255562= has no published release
  artifact and its flake selects =x86_64-linux=. The bounded Nix image build
  (two CPUs, 3 GiB, max-jobs 1, 900-second deadline) failed fetching dependencies:
  =https://cache.nixos.org/nix-cache-info=: =CONNECT tunnel failed, response 403=.
  The host CA was supplied without disabling TLS. No compilation result is
  claimed, and no source rebuild/retry loop was launched after this blocker.
- The 403 is a rejection of =CONNECT cache.nixos.org:443= by the configured
  =http://proxy:8080= HTTPS proxy, before an origin TLS connection/GET
  =/nix-cache-info= was established. It is not an origin 404 or evidence of a
  private Server artifact. The same log records rejection of
  =CONNECT ftpmirror.gnu.org:443= for =/bash/bash-5.3.tar.gz=. This explains the
  subsequent dependency failure. No proxy bypass, alternate mirror, TLS/auth
  weakening, or repeated network probe was used to evade either denial.
- Source-build route inspection at the same Server baseline: README's supported
  reproducible route is Nix; its interactive example still runs =nix develop=
  before =sbcl --load run.lisp=, but =run.lisp= is absent. =make -n build= does
  expose the existing =sbcl= / =ql:quickload= / =save-lisp-and-die= recipe; it
  does not provision Quicklisp/Qlot, native libraries, or a Debian dependency
  closure. The Qlot cl-couch lock is =e3c8e7d1548c7814e49528869c098e5e03ccbe80=,
  whereas the supported flake pins =a37150193b81fad16d24b42102353fcad9c649ad=.
  No SBCL/Quicklisp/Qlot executable or preinstalled dependency closure exists
  in this test environment. This is source-inspected deployment drift, not a
  failed SBCL compilation or proof that ASDF cannot run on Debian. There is no
  documented, self-contained non-Nix Debian deployment route yet. Implementing
  that route is owned by [[https://github.com/lost-rob0t/starintel-server/issues/341][server #341]], separately from native ECL issue #318.
  Missing setup is implementation work, not a reason to substitute another Server.
- The permitted Debian source-build preflight subsequently tried the required
  official Quicklisp bootstrap once at =https://beta.quicklisp.org/quicklisp.lisp=.
  Curl returned exit 56, =http_code=000=, =connect_code=403= and
  =CONNECT tunnel failed, response 403=; the proxy response identifies =envoy=.
  No origin TLS/HTTP response or dependency bytes were obtained. This exact
