#+TITLE: Zara workflow ownership
#+AUTHOR: nsaspy
#+STARTUP: overview

* Scope
The desktop Home Manager profile enables =zara.workflows=.  That module installs
non-secret operator workflow defaults and the bounded =zara-system-update=
helper without taking ownership of Zara's mutable private overlay.

* Configuration ownership
- =.config/zarathushtra/config.pl= is the canonical tracked declarative base layer
  and Home Manager may replace it on activation.
- =~/.config/zarathushtra/config.local.pl= is intentionally not managed by Home
  Manager.  Keep secrets, machine-private facts, experiments, and temporary
  overrides there.  Zara loads it after =config.pl= so local facts win.
- =~/.config/zarathushtra/secrets.env= remains outside Git/Nix and is consumed
  by the existing =zara-server= EnvironmentFile integration.

This split is deliberate: reproducible workflows belong in dotfiles; mutable
private state does not.

* Doom-native Emacs integration
The desktop profile installs the registered =zara-emacs= service plugin and
writes its non-secret plugin configuration to
=~/.config/zarathushtra/plugins/zara-emacs/config.toml=.  The plugin is bound
to Emacs server =doom=, matching the Doom/Home Manager server profile, and uses
=~/Documents/Notes/org= as its Org knowledge root.

Doom itself pins =emacs/zara.el= to the reviewed Zara native-client commit and
enables =zara-native-mode= globally.  Editor control is not implemented as
model-constructed Elisp: the plugin sends base64 JSON requests to the
versioned =ZARA-EMACS/1= semantic bridge loaded inside the running Emacs.
That running Emacs instance remains authoritative for buffers, active modes and
keymaps, windows, modification ticks, ordinary undo, and explicit saves.

The Doom leader surface is:

- =SPC y z z= — Zara chat;
- =SPC y z a= — ask Zara, using the active region when present;
- =SPC y z s= — native Zara/bridge status;
- =SPC y z c= — current structured Emacs context.

After =gptel= loads, Doom registers the native Zara delegation and current
buffer-context tools.  The canonical Zara runtime still owns conversation,
voice, tools, memory and agent behavior; Emacs does not create a second agent
loop.

* Qwen3-TTS backend
The desktop profile imports the =Qwen3-TTS_server= Home Manager flake module,
installs its =qwen3-tts= command, and enables the Vulkan GPU service on
=http://127.0.0.1:7860=.  The service runs the pinned upstream
=qwentts.cpp= GGML image on =/dev/dri= render nodes only; =/dev/kfd= and the
retired PyTorch/ROCm path are gone entirely.  Zara streams speech from it in
real time (s16le 24 kHz PCM) instead of buffering whole WAV files.  Home
Manager deliberately does not own =~/.config/zarathushtra/config.toml=.

Merge this table into that mutable file.  Replace its existing =[tts]= table if
present; TOML does not allow two tables with the same name.

#+begin_src toml
[tts]
provider = "qwen3"
endpoint = "http://127.0.0.1:7860"
voice = "zara"
connect_timeout = 5.0
read_timeout = 120.0
total_timeout = 180.0
#+end_src

The =voice= name must reference a registered clone voice or a model speaker;
create a =zara= voice (below) before switching the provider.

Apply and verify the services:

#+begin_src shell
home-manager switch --flake ~/.dotfiles#unseen@desktop
qwen3-tts doctor vulkan
systemctl --user restart qwen3-tts zara-server
qwen3-tts status
sudo loginctl enable-linger "$USER"
#+end_src

The =loginctl= command makes the user services start at boot without waiting
for an interactive login.  The first Qwen start pulls the pinned image and
downloads sha256-verified GGUF models (0.6B talker plus 12 Hz codec, about
1.2 GB); later starts are immediate.  Persistent models and reference voices
live under =~/.local/share/qwen3-tts= rather than in this repository.

Create and manage voices from any FFmpeg-supported audio or video source:

#+begin_src shell
qwen3-tts voice add zara ~/clip.mp3 --text "Exact words in the clip."
qwen3-tts voice add guest ~/video.mp4 --start 00:01:12 --duration 12
qwen3-tts voice list
qwen3-tts voice info zara
qwen3-tts voice set-text zara "Corrected exact words."
qwen3-tts voice rename guest narrator
qwen3-tts voice export narrator ~/narrator.wav
qwen3-tts voice remove narrator
#+end_src

Use =--replace= with =voice add= to update an existing name.  Supplying the
exact =--text= persists a same-stem =.txt= transcript next to the voice WAV,
which the server registers for higher-fidelity ICL clone mode; without it the
voice falls back to the x-vector-only path.  After changing =voice= in
=config.toml=, restart =zara-server=; adding or replacing the referenced clip
itself does not require restarting Qwen.

The Vulkan backend needs Docker access plus host =/dev/dri= with a render
node (=renderD128=); it never touches =/dev/kfd=, and GGML keeps its compute
queue off the graphics queue so the desktop session is not the failure
surface.  Validated live on the RX 5500 XT (RDNA1): model load, 896 MB
KV-cache allocation, synthesis, and realtime streaming all pass with zero
kernel GPU faults.  On hosts without a usable Vulkan driver use
=backend = "cpu";= as the explicit emergency mode.

* Authenticated Android listener on flake
The =unseen@flake= Home Manager profile starts Zara with its owner-private IPC
endpoint for local clients and an authenticated TCP listener on all IPv4
interfaces at =tcp://0.0.0.0:6060= for Android. The phone connects to the host's
LAN address, currently =tcp://10.50.50.28:6060=. Its existing CURVE/ZAP identity and client
registry remain outside Nix and Git under
=~/.local/state/zarathushtra/security=. Other desktop profiles retain only
local IPC. The Zara flake input is pinned to the tested GitHub merge commit.

Apply the flake user-service configuration with:

#+begin_src shell
home-manager switch --flake ~/.dotfiles#unseen@flake
#+end_src

Verify the local listener with:

#+begin_src shell
systemctl --user status zara-server --no-pager
ss -ltnp | grep ':6060'
journalctl --user -u zara-server -n 100 --no-pager
#+end_src

The phone must pin this server's public key and its CLIENT PUBLIC KEY must be
enrolled in the server registry. The service has no unauthenticated fallback.
Port access from the phone still depends on the host and LAN firewall policy.

* Operator workflows
The canonical fact definitions live in
[[file:../../.config/zarathushtra/config.pl][config.pl]].  They cover
Brave/search, Emacs scratch, org-roam daily followed by the existing
=zara-dictate= path, Thunderbird, Tor Browser, Feishin, YouTube Music, GitHub PR
compatibility, Magit project aliases, and =/pol/=.  The 4chan mapping carries a
small explicit alias set for common text/ASR forms; general edit-distance/fuzzy
resolution belongs in Zara Core rather than being simulated by an unbounded
alias list here.

* System update boundary
=update system= resolves to =zara-system-update=.  The helper performs the three
operator-requested steps in order:

1. =pkexec /usr/bin/pacman -Syu=;
2. =git -C "$DOTFILES" pull --ff-only=;
3. =home-manager switch --flake ...=.

A failing step aborts the sequence and the helper never reports complete unless
all three succeeded.  It never embeds or pipes a password and does not add a
passwordless privilege rule.

The default dotfiles checkout is =~/Documents/Projects/dotfiles=.  Override it
with =ZARA_DOTFILES_DIR=; =ZARA_HOME_MANAGER_FLAKE= and
=ZARA_HOME_MANAGER_TARGET= control the Home Manager invocation when needed.

* Verification
Run:

#+begin_src shell
bash tests/zara-workflows.sh
nix eval --raw '.#homeConfigurations."unseen@desktop".activationPackage.drvPath'
#+end_src

The dedicated Zara workflow Actions job also runs the contract on relevant
