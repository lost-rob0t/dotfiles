The service uses the underlying =config.codex.package=, not the capture wrapper,
and sets =CODEX_HOME= consistently with the Codex module's XDG preference.
Managed ChatGPT authentication must already exist there. Nothing initiates a

For z.AI, the optional private runtime environment file defaults to
=~/.config/llm-log/quotas.env= (or the configured XDG config home). Set
=llm.quotaTelemetry.environmentFile= to use another path. It may contain
=LLM_LOG_ZAI_KEY_FILE=/absolute/path/to/private/key= or =ZAI_API_KEY= supplied
privately by the operator. Keep the environment and key files owner-only (0600).
Do not put secret contents in Nix expressions, repository files or widget options.
The leading optional marker in the unit means a missing file does not prevent
llm-log from starting; z.AI remains unavailable until authentication is supplied.

* Deployment boundary
The Python llm-log service must expose =/api/v1/quotas= and
=/api/v1/stats/timeline?coverage=fields=. The Common Lisp forwarding executable
is a different runtime and does not expose these APIs.

Apply the reviewed Home Manager change, restart the user llm-log service and
reload the installed Qtile configuration. These repository changes do not
activate a live host by themselves. Missing/offline/expired values are not green
zeros. Local integration used synthetic account metadata and offscreen Cairo;
actual provider login and the user's live desktop remain a separate smoke test.


* StarIntel worker admission
The StarIntel harness consumes the same provider-reported =/api/v1/quotas=
snapshot as the desktop meters. It does not infer capacity from the strings
"Pro", "Max", model names, captured token counts, or local request history.

Each GPT and z.AI window must independently admit a new worker. The default
policy retains 10% reported headroom and paces the spendable portion across the
provider's reported window, with a small 5% burst. A stale, missing, unknown, or
expired meter fails closed. Cross-process concurrency and launch intervals are
also bounded locally.

The harness config is generated at =~/.config/starintel/llm-harness.json=.
The default =main= profile uses Codex in a read-only planner sandbox, validates
the returned plan with SWI-Prolog, can allocate up to 15 named specialist worker
slices, executes GLM-5.3 work through Prolog-RLM and the =zai= llm-log prefix,
and requires independent Codex plus GLM reviews. Logical fan-out is separate
from physical provider concurrency: quota pacing, reserve floors, and launch
leases remain authoritative. The
=main-direct-glm= profile keeps the same planner/review gates but executes
through =opencode-worker=.

These controls pace only harness-originated work. Other clients can still spend
the account allowance; their usage is reflected by the next authoritative quota
snapshot.
The Prolog-RLM GLM wrapper reuses the same private runtime credential source as
quota telemetry: =llm.quotaTelemetry.environmentFile=. It accepts only
=ZAI_API_KEY= or =LLM_LOG_ZAI_KEY_FILE= from that file, requires the environment
file and referenced key file to have no group/other permission bits, and never
sources the file as shell code. Secret contents are not serialized into the
generated harness JSON or Nix store configuration.
